# turn-recovery

## 目标

一次中断不应该让已完成的工作白做。三层恢复按代价从低到高排列，前一层能解决就不惊动后一层：

1. **调用级重试**（`llm-retry`）：单次模型调用的瞬时故障，自动退避重试；
2. **步骤级重试**：流吐到一半才断，重跑这一步，并让界面丢掉半截文本；
3. **任务级续跑**：重试仍然失败，用户点「继续执行」，新一轮带着**上一轮的计划与已完成的步骤**
   接着跑。

## 步骤级重试

- `chat.Config.StepRetry retry.Policy`；`Request` 不覆盖它（它是 runner 的部署级策略）。
- 触发条件是"**这一步**的模型调用失败"，无论失败发生在第一个 chunk 之前还是之后。
- 重试前先发 `step_retry`，让客户端清掉这一步已经收到的文本/思考：

```json
{ "type": "step_retry", "step": 3, "attempt": 2, "max_attempts": 3,
  "delay_ms": 1600, "error": "unexpected EOF" }
```

  - `attempt` 是**本次即将进行的尝试**的序号（首次为 1，第一次重试为 2）。
  - 客户端必须把该 step 的 `text` / `reasoning` 清空，并显示一行"第 2/3 次尝试，1.6s 后重试"。
- 重试不再执行的情况：错误不可重试（`Retryable() == false`）、attempt 用完、调用者取消、
  本轮墙钟预算不足以再等一次（此时 sleep 被截到剩余时间，剩余为 0 就直接放弃）。
- 重试之间**历史不变**：失败的那次没有产生 assistant 消息（它没有完成），所以重跑用的是同一
  份历史。这保证重试不会把半截回答喂回模型。
- 放弃时走进今天已有的失败路径：`error` 事件 + 落库（带错误文本），界面照旧显示失败。
- 一次 turn 内的重试总量有上限：`max_steps × max_attempts` 是硬上限，并且 token/时间预算仍然
  是最终闸门。

## 任务级续跑

### 端点

```
POST /api/chat/sessions/{id}/resume     body: {} （可省略）
```

- `202 {"turn": {"session_id", "streaming": true, "started_at"}}` —— 与 `POST /messages` 同一
  形状，客户端随后照常 attach 到 `GET /chat/sessions/{id}/turn`。
- `409`：会话已有轮次在跑（同一轮一会话的规则不变）。
- `400`：没有可接续的东西（既没有上一轮的 assistant 记录，也没有未完成的计划），响应里给出
  可读原因。
- 服务端在续跑前会：读上一轮的落库记录（`chat_messages.steps` 里的步骤与工具观察、`error`、
  `stop_reason`）、读当前计划、取最后一条 user 消息作为原始目标。

### 注入的上下文

- 会话里留一条**可见**的用户消息：`继续执行（从上一轮中断处，共 N 项未完成）`。
- 模型的上下文里额外注入一条接续简报（不落库、不出现在界面上），内容固定为下列小节：

```
[接续执行] 上一轮没有跑完，现在从中断处继续。不要重做已经完成的工作。

【原始目标】<最后一条 user 消息>
【中断原因】<error / stop_reason>
【计划现状】已完成 a/b：<渲染好的清单>
【上一轮已完成的步骤】
- 步骤 1：<该步说了什么> · 工具 read_file(x.go) ok
- 步骤 2：… · 工具 bash(go build) 失败：…
【最后一段输出（可能被截断）】
<...>
- 工具输出按条截断到 800 字符，整份简报上限约 6000 字符；被截断时明文说明。
请先 plan_read 确认计划现状，然后从第一个未完成的任务继续；已经完成的步骤不要重复执行。
```

- 简报里"已完成"的判定：`error == "" && stop_reason == ""` 的上一轮 = 它自己收的尾，此时
  只把计划未完成项当作待办；否则把**未完成计划 + 最后一个未完成步骤**当作接续点。
- 简报是**提示**而不是事实来源：模型被要求必要时重新执行只读命令确认现状（写操作不要重放）。
- 续跑本身也是一轮普通 turn：预算、工具集、工作区、计划工具全部照旧；计划若不存在，模型
  被要求先 `plan_create`。

### 界面

- 看板上的「继续执行」在**计划有未完成项且没有轮次在跑**时出现；点击行为与发消息一致
  （立刻显示用户气泡 → `POST .../resume` → attach）。
- 失败轮次的消息气泡上同样提供「继续执行」（与「重试」并列：重试是重发原话，继续执行是接着
  跑）。

## 边界

- 不做自动续跑（无需人确认就接着花钱）。
- 不重放工具结果到模型历史里作为真实 tool 消息：那会要求每一条 tool_call 都有配对结果，而
  中断的轮次正好缺配对。简报是文本，不是伪造的工具交换。
- 不保证"接着跑"一定成功：它保证的是模型**知道**已经做到哪、不用重新想一遍。
