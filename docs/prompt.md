# 系统提示词：模型每一轮先读到的那段规则

huan-agent 每发一次模型请求，都先放一条 system message。那段文字决定了模型把自己当成什么、怎么说话、怎么动手，以及它以为自己能做什么。它不控制权限——权限是注册表决定的，工具没注册就是不存在——它控制的是模型有没有把已经给它的能力用对。

## 提示词在哪

| 文件 | 内容 |
|---|---|
| `internal/prompt/base.md` | 通用 Agent 基础提示词：身份、语言与表达、做事方式、工具使用、边界与安全。所有界面共用。 |
| `internal/prompt/surface_web.md` | Web 控制台独有的规则：Markdown 渲染、附件、`ask_user` 卡片、任务计划（`plan_*` 工具与任务看板）、被中断后接着跑。 |
| `internal/prompt/surface_cli.md` | `huan-agent chat` 独有的规则：终端纯文本、没有交互卡片。 |
| `internal/prompt/surface_feishu.md` | 飞书独有的规则：卡片渲染、超宽表格会被拆成多条消息、没有 `ask_user`。 |
| `internal/prompt/prompt.go` | 拼装：`prompt.Base()` 给出基础提示，`prompt.For(surface)` 给出「基础 + 该界面的段落」。 |

这些 markdown 用 `go:embed` 打进二进制：改完要重新 `make build`（`go test ./internal/prompt/...` 不需要重新构建，它直接读这些文件）。

## 各界面拿到的是什么

| 界面 | 提示词 | 覆盖方式 |
|---|---|---|
| Web 控制台（对话） | `prompt.For("web")` | `chat.system_prompt`（Web Admin 的对话配置块，留空即默认） |
| 飞书机器人 | `prompt.For("feishu")` | `chat.system_prompt`，同一个字段 |
| `huan-agent chat` | `prompt.For("cli")` | 命令行的 `--system`，或 `--skill`（技能正文本身就是提示词） |

覆盖规则只有一条，实现在 `prompt.Effective(override, surface)` 里：**填了就整套替换默认提示词**（连该界面的段落一起），只填空白等于没填。控制台和飞书机器人共用 `chat.system_prompt` 这个字段，所以两者不会在「谁的提示词优先」上分叉；命令行不读它，`--system` / `--skill` 就在手边，多一个隐式来源只会让人猜这一次到底生效了哪一份。

覆盖面要说清楚：`chat.system_prompt` 是**进程启动时**从 `configs/config.yaml` 读的，改了要重启（`make run` / `make run-admin`）。`chat` 块里能被 设置 → 对话预算 在运行时覆盖的是三个预算字段，提示词不在其中。

技能的**可用技能**段落不在这个包里：它由 `internal/server/skilltool.go` 每轮拼在系统提示后面，因为技能是否启用是数据库里的状态，不是编译进二进制的文本。飞书机器人不拼这一段（它没有技能面板）。

## 两条硬性约束

**一、全中文。** 工具描述、技能段落、控制台界面都是中文，模型读到两种语言只会犹豫该听谁的。`internal/prompt/prompt_test.go` 里有一条测试专门拦英文散文——它放行工具名、路径和命令行开关（这些本来就是 ASCII），拦下 `the` / `and` / `should` 这类英文虚词，并检查汉字占比不低于一半。

**二、体积有预算。** 一轮 turn 里**每一步**都会把 system 提示原样带上：`context.max_tokens` 的循环内压缩也逐字保留它，因为那是这一轮的行为准则。所以提示词的体积不是「一次」的成本，而是「每一步 × 步数」。同一个测试文件里有一条 12 KiB 的上限——现在基础提示约 5 KiB，涨到两倍以上就该想想是不是把该写进技能或工具描述的东西写进了通用提示。

## 改提示词的检查清单

- **工具改名**：提示词里出现的每个工具名（`read_file`、`edit_file`、`bash_background`、`bash_output`……）都要一起改。模型不会调用一个它没听说过的工具，而它会调用一个提示词里写着、注册表里却没有的工具——那是一次必然失败的调用。
- **新增界面**：加一个 `surface_*.md`，在 `prompt.go` 里注册一个 `Surface*` 常量，然后**明确写下这个界面没有什么**（有没有卡片、能不能提问、输出会不会被截断）。缺省地不发段落也是对的：模型会退回基础提示里「工具列表就是能力边界」这条规则。
- **加了新能力**：先把规则写进工具描述（模型每次都能看到它），只有「跨工具的行为准则」才值得放进通用提示。工具描述比系统提示便宜：只有本次请求带上它们，而系统提示每一步都在。
- **改完跑**：`go test ./internal/prompt/...`（语言、体积、各界面的段落），以及 `go test ./internal/server/...`（控制台把基础提示 + web 段 + 可用技能段拼起来的顺序）。

## 为什么不照搬 Claude Code / DeepSeek Harness 的提示词

那两份提示词里有一半在描述它们的工具集（子 Agent、计划模式、任务清单、技能市场）。huan-agent 现在有任务清单（`plan_*` + 任务看板），那一节的规则就是照着它们写的；其余几样没有，写进去只会得到一段模型无法执行的规则。能搬的是它们**关于行为**的那部分，也是这里的通用提示词真正借鉴的东西：

- 先查证再断言，先读文件再改文件；
- 一次把事做完，而不是停在建议上；
- 改得小而准，不做没被要求的重构；
- 动手前说一句要做什么，收尾时如实说改了什么、验证了什么；
- 不确定就说不确定，没验证就说没验证。

这些和具体工具无关，也正因如此它们值得占每一轮的那点 token。
