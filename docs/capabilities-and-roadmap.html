六项核心能力的水位

长上下文

1M token 从「卖点」变成「默认」，几家的旗舰都在这一档。技术侧的关键变化是稀疏注意力让长上下文的成本塌了：MiniMax 的 MSA 设计把 1M 上下文下的单 token 计算降到上一代的约 1/20，预填充快约 9 倍、解码快约 15 倍。

  • GPT-5.6 三档（Sol / Terra / Luna）均为 1M 窗口
  • Gemini 3.1 Pro 报称 10M，是已公布的最大窗口
  • Kimi 宣传 200 万字符级上下文，面向整库代码与长视频
来源：iternal.ai / ideas2it.com / bentoml.com / 峰会介绍页

原生多模态

不再是「文本模型加一个视觉编码器」，而是在同一套表示里处理图文音视频。国产模型这一轮跟得很紧，Omni 类模型把「看懂、听懂、直接行动」合到一个模型里，省掉了跨模型串联的延迟与信息损失。

  • Qwen3.5-Omni / MiMo-V2.5：视觉 + 听觉原生融合
  • Step-3.7-Flash：直接吃 UI 界面、图表、文档，输出结构化结果
  • Grok 4.3：加入原生视频输入
来源：知乎模型汇总（2026-09-09）/ bentoml.com / aimlapi.com

推理与思维链

「思考档位」成了标准配置：同一个模型提供 none / low / high 多档推理强度，让调用方按任务难度换成本。前沿差距收窄到个位数百分点，开源模型已经挤进第一梯队。

  • Claude Opus 4.8：GPQA 93.6%
  • GLM-5.2（开源，MIT）：GPQA 91.2%，ARC-AGI-2 22.8%
  • Step-3.7-Flash：低 / 中 / 高三档推理层级可选
来源：iternal.ai / 知乎模型汇总

工具调用与 Agentic

从「会调函数」升级为「能长程执行」：拆解目标、跨工具串联、失败后自己改策略、跑到环境里验证结果。MCP 与 Skills 事实上成了工具接入的通用协议，模型厂商开始针对主流 Agent 框架做兼容优化。

  • GPT-5.4：原生电脑控制 + 响应中途可控（mid-response steerability）
  • Step-3.7-Flash：针对 Claude Code / MCP / Skills 做兼容优化
  • 企业侧：97% 企业已探索智能体战略，49% 已将近半数项目转正式应用
来源：zte.com.cn / 腾讯云开发者社区 / 头豹研究院引 OutSystems

编码与工程

SWE-bench 类仓库级任务成了主战场，水位从「补全函数」推到「关掉一个 issue」。开源模型在这一项上追得最快——闭源的优势主要体现在最难的推理与最复杂的多模态工作流上。

价格不再是前沿能力的门槛。MoE 与高效架构普及后，同代能力的调用价格差出两个数量级；开源权重模型开始咬住闭源旗舰，且大多用 Apache 2.0 / MIT 这类宽松许可。

关于上面这些数字的可信度

这一节的数据来自第三方汇总站点、厂商宣传页与媒体报道，不是官方 benchmark 榜单。 同一个模型的上下文窗口在不同来源里能差一个数量级（例如 Gemini 3.1 Pro 有 1M 与 10M 两种说法）， 因为「原生窗口」「可扩展窗口」「API 实际生效窗口」是三件事，各家口径不一。

把它当成「量级参考」而不是「精确指标」：绝对值不可全信，但趋势（上下文变长、多模态原生、成本下探、 开源追赶）在多个独立来源里一致，这部分是可靠的。每一项的具体链接见页面末尾。

Part 3 · 行业

演进方向：还没解决的事趋势

下面四条是行业层面的「未来规划」——不是某个厂商的路线图，而是从当前公开信息里 能看出的、整个方向正在撞的天花板。这一节与后面的项目待办是两回事：这里是行业的， 后面是 huan-agent 自己的。

方向 01

上下文：从「更长」转向「更有选择」

1M 已经是标配，继续堆到 10M 的边际收益在下降——注意力在超长文本里会稀释， 全量塞进去的代价是成本与「中间遗忘」。接下来的竞争点是选择性地看： 检索、压缩、分层记忆，以及在推理过程中主动回查而不是一次性读完。

方向 02

Agentic 的可靠性，而不是能力上限

单步能力已经够用，卡住的是长链路：几十步之后是否还守着最初的目标、 出错后能不能识别并回退、能不能判断「该停下来问人」。 Gartner 的 80% 部署预测背后，真正的瓶颈从模型能力变成了流程可观测性与权限治理。

方向 03

成本与延迟的持续下探

MoE、稀疏注意力、推理缓存让同代能力的价格每年往下走一个台阶。 结果是「用得起」不再是限制，「用得多快」成为限制， 于是速度指标（tok/s）第一次和智能指标并列出现在选型表里。

方向 04

互操作协议收敛，但治理没跟上

MCP、Skills、function calling 正在收敛成事实标准， 模型可以被不同宿主复用。但企业侧的审计追踪、权限边界、数据合规仍处在早期—— 97% 企业在探索、只有一半走到正式应用，差距就在这一层。

能力是怎么被记录的

两块信息，两种来源

llm_models 表对每个模型记两件事：能干什么（capabilities） 和窗口多大（context_window），并且各自标注来源， 因为它们的可信度不一样：

  • context_window：71 / 72 个来自 api —— 网关在 /models 响应里直接报的数，是厂商会真正执行的限制，最可信
  • asked = 直接问模型自己「你支持图像输入吗，窗口多大」， 网关不报时的兜底手段
  • api（能力列）= 从网关公布的 endpoint 反推，例如 /chat/completions 能证明会聊天
  • 但能力列有 65 / 72 个来源为空，而这 65 个并不都是「没问过」—— 见下方「一处口径缺陷」
依据：llm_models 表 capabilities_source / context_window_source 计数

这个设计背后的判断

代码里写明的原则是：「缺少证据不等于没有能力」。 接口列表里没有 /audio/speech，只能说明网关没列， 不能证明模型不会说话——所以缺失一律不当作否证， 而是留成空值等下一次真实提问。

  • 窗口自动推导：窗口 × window_ratio − reserve_output_tokens
  • 不认识的模型用 default_window（默认 131072）保守估
  • 上下文压缩在 context.max_tokens: 60000 处触发，把旧消息折叠成摘要
依据：internal/llm/catalog.go 注释、configs/config.yaml:153-169
一处口径缺陷：能力列的来源标注是断的，别把它当可信度指标

核对时发现，「能力已确认」这个说法对这批数据不成立，原因在代码里：

刷新模型列表时，internal/server/modelrefresh.go:167 会用 llm.InferCapabilities(info.ID) 从模型名字猜能力 （名字里有 gemini、vision、-vl 等字样就加上 vision）， 但这个写入路径没有设置 capabilities_source， 于是在库里留下了「有 vision 但没有来源」的记录。

而 internal/store/catalog.go:340-341 定义了本该标记这种情况的常量 ModelCapabilitySourceInferred = "inferred"——全仓搜索确认， 这个常量除了定义处，没有任何地方写入或读取它。

实测后果：10 个模型带 vision / tools 标记，其中 7 个其实源自名字猜测 （6 个 gemini、1 个 deepseek-v4-flash-vision-exp）， 只有 3 个是真问来的（MiniMax-M3、Qwen3.7-Max、Qwen3.7-Plus）。 所以下面表格里的「能力来源」列读法应该是： asked / api 可信，空白则是「推断，但没标出来」， 而不是「未知」。这是这一页里唯一一处我推翻了自己先前说法的地方。

Part 6 · 本项目

还没做完的事7 项

按优先级排，每条都带可复现的核实命令与实测输出。前两条是「在写下一行代码之前处理」， 后面五条排队即可。数据核实时间 2026-09-18 / 09-19。

P0-1

trace 数据无裁剪，数据库已在无界增长

这不是风险，是正在发生的事实：本机 5 天涨到 191MB，其中 observations 表占 148MB。 设计早就写在 phase-5c 的 tasks.md 里，只是代码没写。
实测
$ ls -lh data/huan-agent.db 191M $ sqlite3 data/huan-agent.db "SELECT COUNT(*), SUM(LENGTH(input))/1048576 FROM observations;" 2912|148 # 单 input 一列占 148MB $ sqlite3 ... "SELECT type, COUNT(*), SUM(LENGTH(input))/1048576 FROM observations GROUP BY type;" GENERATION|1216|148 # 体积全在模型调用上，工具调用几乎不占 SPAN|1696|0 $ grep -rn "PruneTraces\|ClearTraces\|retention" --include=*.go . | grep -v _test.go （零命中） # 只写读，没有删
成因（已修正过的判断）

增长是 线性 + 平台期，不是 O(n²)。每步存完整 message 列表且无长度上限， 但仓库里有活的上下文压缩在兜底：逐步骤体积的斜率递减 （+5.8 → +4.1 → +1.7 KB/step），在约 480KB 处饱和， 第 121 步触发压缩后断崖回落到 18KB。 所以压缩只管住「每步多大」，没人管「总共留多少」——真正的解法是裁剪，不是加长度上限。

要做

1. store.PruneTraces(retention_days, max_traces) + 启动时跑一次， 配置项走 viper.SetDefault（tracing.retention_days 默认 14、 tracing.max_traces、tracing.prune_interval）—— 这一条是让表有界的唯一一件。
2. 写入侧加长度上限（单条 input 超 64KB 只存尾部 + truncated: true）—— 常数改善约 3.7 倍，但消不掉「无界」。
3. ListTraces 的 SELECT 去掉 input, output（列表页不显示，实测快 8.5 倍）。
4. 裁剪必须配 VACUUM——实测 freelist_count=0、 auto_vacuum=0，DELETE 不会把空间还给文件系统。phase-5c 的设计漏了这一步。

P0-2

run 的写权限与保护措施强耦合，要么全信任、要么全残废

huan-agent run 是接进 CI / git hook / cron 的唯一入口， 现在只有两个档位，没有中间态。这挡住了所有可托付的自动化场景。
两个档位
// 档位一（默认）：完全信任 tools.read_only = false // 有完整写权限 tools.enable_bash = true tools.approval.mode = off $ grep -n checkpoint cmd/huan-agent/run.go （零命中） // 也没有回滚 // 档位二（配了审批）：完全残废 cmd/huan-agent/approval.go:36 → SurfaceRun 落进 default → canAsk = false → wrap() 返回 nil, false → 工具从清单里整个摘掉（不是拒绝，是「从未提供」）
为什么这是问题

代码注释自己承认了这个取舍，理由是「refused 比 absent 更糟」—— 这个理由对交互式场景成立，对 CI 不成立：CI 里没人看，但执行者（CI 脚本）可以事先声明权限。 「按策略需要确认但无人在场 → 那就别做」是正确的； 「于是连读带写的工具全摘掉，任务整个无法完成」不是。
结果：不配审批 → 它能在 CI 里跑 git push；配审批 → 它什么都干不了。两者都不可托付。

要做

给 run 一个非交互的权限档位——显式声明，而不是「配了审批」的副作用。 原则：边界用档位，便利性才用正则，顺序不能反。

顺序依赖

先 P0-1 再 P0-2，不能反。反过来的话，run 每跑一次就往同一张无界表写一份 trace， 增长速率会从「跟开发时长挂钩」变成「跟提交频率挂钩」。

P1-4

ask_user 与审批卡片只有 Web 有，飞书路径能力残缺

交互式能力被绑死在 Web 一个界面上， 意味着飞书 bot 上的写操作要么无审批、要么被静默摘掉。
// cmd/huan-agent/chat.go:530 if opts.Surface == "web" { /* ask_user 注册 */ } // cmd/huan-agent/chat.go:551 if opts.Surface == "web" && cfg.Chat.Plan.Enable { /* plan_* 注册 */ } // cmd/huan-agent/approval.go:36-40 case prompt.SurfaceWeb: return true case prompt.SurfaceCLI: return true default: return false // 飞书 + run

飞书审批卡片是 Phase 21 明确的「不做」项，所以这是已知取舍而非疏忽。 但它与 P0-2 叠加后意味着：三个非 Web 路径（CLI 的 plan/ask、飞书、run）能力明显更弱。 CLI 有补偿（REPL 支持 /rollback，检查点是通的），飞书与 run 没有。

P2-5

没有 MCP server 模式

go.mod 里有 mcp-go v0.54.1，但只在测试里当假 server 用。 生产代码没有把自己暴露成 MCP server 的入口，子命令只有 admin / serve / chat / run / usage / viking / version。 不能被调用 = 进不了别人的工作流（Cursor、Claude Code 这类生态）。 需要自己的 capability，尚未排期。
P2-6

没有 Dockerfile / 部署外壳

仓库根目录无 Dockerfile / docker-compose.yml / .dockerignore。 单二进制 32MB + SQLite 单文件 + 前端 embed，容器化成本很低， 但 PLAN.md Phase 6 计划过、一直没做。
P2-7

文档滞后于实现

docs/status.html 停在 Phase 9（缺 8 与 11–24）； openspec/specs/project.md 的 Capabilities 表停在 phase 7； 28 个 change 里只有 4 个归入 archive/， 其余 23 个含 phase-6 到 phase-24 全部还挂在 changes/。 这是维护债，不是能力缺口——建议在归档 P0 改动时一并清一轮。
